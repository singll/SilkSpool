# 案例：授权服务器 redirect_uri 校验不严、把授权码送到攻击者地址（高危）

> 来源: https://nvd.nist.gov/vuln/detail/CVE-2019-3778 · CWE: 603 · 首发年份: 2019
> 关联: rules/techniques/oauth-jwt-test.md · VC 卡: 无

## 模式（什么形状的目标会有这洞）
目标自己当 OAuth 授权服务器（给第三方应用发授权码），授权口的 redirect_uri 校验用了默认解析器且规则太松：子域通配、路径前缀匹配、大小写/编码差异放行。框架级实现让缺陷跟着每一个用默认配置的接入方走。

## 打法（案例里实际打通的路径）
先收集合法 redirect_uri 的形状（接入方文档、抓包、应用市场详情）。在授权口把 redirect_uri 换成绕过变体：大小写、编码、路径穿越回到白名单前缀再跳出、借白名单域下的开放重定向兜一跳（变体清单见 oauth-jwt-test 模块）。发起一次完整授权，看浏览器最终带着 code 落在哪——落点可控即码被截。再补一枪：拿截到的码换 token，证明真能进受害者账号。

## 出什么算成
授权流程完成后，授权码（或隐式流的 token）出现在你控制的地址，且能换成有效访问令牌。

## 假点（什么样不算）
redirect_uri 精确匹配白名单，任何变体都回 invalid_redirect_uri；码被 PKCE 或一次性消费绑定换不走——截到码但换票失败时如实写"配置弱点、接管未成"。

## 为什么值钱（severity 依据）
授权码是账号接管的最短路径，框架级缺陷波及所有默认配置的部署，厂商按高危起步收。
