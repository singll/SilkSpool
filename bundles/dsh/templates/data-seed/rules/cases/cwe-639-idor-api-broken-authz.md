# 案例：公共服务平台内部数据 API 只验登录不验数据归属（高危）

> 来源: https://krebsonsecurity.com/2018/11/usps-site-exposed-data-on-60-million-users/ · CWE: 639 · 首发年份: 2018
> 关联: rules/techniques/idor-test.md · VC 卡: 无

## 模式（什么形状的目标会有这洞）
平台给企业客户上了大数据/追踪/可视化类分析产品，几十个内部查询接口共用一套"已登录即可"的闸：会话只证明你是本站用户，不证明你查的数据属于你。目标画像：大厂主站之外挂着"数据服务/报表/开放平台"类子域，接口名带 query/report/batch，入参是用户名、账号 ID 或批次号而非"查我自己"。

## 打法（案例里实际打通的路径）
注册一个最低权限普通账号登录该子域，把内部 API 清单抓全。挑一个查询口，把入参里的用户名/账号标识换成别人的——先用注册流程或公开资料确认一个真实存在的号。观察回包：出现对方的联系方式、账户状态、在途数据即中。再补写口：改资料/改偏好的接口同样只看登录不看归属。全链不需要任何高权操作，普通号改一个参数就完事。

## 出什么算成
普通账号能查到（或改到）**他人**的账户资料/业务明细；对照换成自己的标识时只回自己的。

## 假点（什么样不算）
入参换号回空或报错；接口本来就是公开查询（数据无 PII、人人可查）；换号后回的是脱敏聚合数据而非个人明细。

## 为什么值钱（severity 依据）
影响面直接乘上全平台用户量（判例是 6000 万用户），且读+写全开，平台按"大规模隐私泄露 + 可篡改他人资料"收高危。
