# 案例：缓存键之外的头与参数决定响应内容、一次投毒全站受害（高危）

> 来源: https://portswigger.net/blog/practical-web-cache-poisoning · CWE: 444 · 首发年份: 2018
> 关联: rules/techniques/cache-poisoning-test.md · VC 卡: 无

## 模式（什么形状的目标会有这洞）
CDN 只拿 URL（部分头）当缓存键，但后端生成响应时还读了其它输入：X-Forwarded-Host 等转发头、X-Original-URL、参数顺序。这些"非键输入"就是投毒把手——你存进去什么，后续所有访问这个 URL 的人拿到什么。

## 打法（案例里实际打通的路径）
先找非键输入：逐个加/改候选头与参数，看响应体或响应头是否跟着变（可工具化识别，清单见 cache-poisoning-test 模块）。确认某个输入进内容后，把它设成你的载荷——重定向到钓鱼域、注入指向你域的脚本资源——刷一次让缓存收下。再用干净环境访问同一 URL 验证拿到的是你的载荷。升级路径：fat GET（GET 带 body）、DOM 投毒、Vary 头组合绕过。

## 出什么算成
普通用户访问官方 URL 拿到的是你注入的内容（脚本执行或重定向到你域），且有缓存 HIT 证据。

## 假点（什么样不算）
非键输入只影响你自己这次响应、缓存不存；后端不读任何非键输入（怎么改响应都一样）；只能投毒自己会话态的 URL（别人拿不到）。

## 为什么值钱（severity 依据）
一次投毒、全体用户受害；能当存储 XSS 用而站点本身没有注入点。原研究在多个头部站点实测可打，收高危到严重。
