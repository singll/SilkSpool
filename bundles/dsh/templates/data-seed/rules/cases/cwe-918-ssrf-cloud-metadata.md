# 案例：SSRF 打云元数据服务、换 IAM 临时凭证拖走对象存储（严重）

> 来源: https://krebsonsecurity.com/2019/07/capital-one-data-theft-impacts-106m-people/ · CWE: 918 · 首发年份: 2019
> 关联: rules/techniques/ssrf-test.md · VC 卡: 无

## 模式（什么形状的目标会有这洞）
目标跑在云上，且存在替用户发起请求的功能：图片获取、URL 预览、Webhook、导入导出、文件转换。边界对内网地址拦得不彻底。云上还有一台"不用钥匙的仓库管理员"——实例元数据服务，谁够得着就发当前角色的 IAM 临时凭证。判例里这枪打在配置失误的 WAF 实例上，凭证到手直通对象存储。

## 打法（案例里实际打通的路径）
先按 ssrf-test 模块做回环与网段对照，确认服务端真的替你发请求、且元数据路径没被封（各云厂商路径差异见模块表）。拿到 IMDS 返回的角色名后取该角色的临时钥匙。钥匙到手别停：用 SDK/API 面列桶、下载对象，一路摸到数据库备份、用户导出件。只回显内网 500 不算数，凭证可用才算通。

## 出什么算成
拿到可用的云临时凭证，并证明它能列出/读到目标账号下的真实业务数据。

## 假点（什么样不算）
边界对元数据端点封死；IMDSv2 强制 token 且拿不到；凭证权限太窄列不出任何东西——如实降级，别脑补"接管全账号"。

## 为什么值钱（severity 依据）
一把 SSRF 直接换到海量用户数据的钥匙：判例 1.06 亿人信息被拖，是 SSRF 家族的天花板判例，收严重。
