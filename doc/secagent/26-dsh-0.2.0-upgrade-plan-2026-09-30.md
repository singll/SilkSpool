## 1. 结论、范围与实施建议

**建议升级到 rc.2，但必须先完成现有升级工具的同格式升级适配、第三方插件兼容处理和隔离预演。现在不能只改版本号运行原升级脚本。**

收益集中在工具调度异常后的可继续性、Web 会话恢复、设置与预设交互、模型目录和长会话显示性能。对 SilkSecAgent 最重要的不是 Desktop 新功能，而是工具结果与任务状态能否一致、模型供给和预算链路能否持续、旧会话和既有配置能否完整保留。

本次与 0.1.5→0.1.7 的区别：

| 维度 | 上次升级 | 本次升级设计 |
|---|---|---|
| 会话 | V3→V4，相邻代次转换 | **V4→V4**；保留日志，验证新旧读取与新事件，不能复用“生成新代次文件且目标不得存在”的发布逻辑 |
| 预设 | `.agent-presets`→bundle patch | 保留已有 7 个受管 preset 和用户修改，只验证目标组合，不再重建旧目录 |
| 设置 | `settings.yaml` 一次性导入 profile | 以当前 web/headless profile 与高优先级 patch 为真相源，不把 `.imported` 再当迁移源 |
| 插件 | auth/bill/failover 升版并补齐 V4 | auth 需覆盖 0.2.0；bill 新版可收敛补丁；failover 最新版仍有版本声明及通知写入问题 |
| 调度 | 官方 schedule 已决定不接入 | 维持自研 task 域唯一调度；适配官方 schedule 三行从基础组合移除 |
| 新交互 | 原阻塞问答 | rc.2 新增可选 timed 问答；本轮默认保持 legacy，后续独立评估 |
| 上线门禁 | U0–U4、冻结、四根切换、不变量、回滚 | 继承完整流程；新增同格式日志保护、模型引用扫描、配置保存、上传关闭、双版本读回 |

**本轮包含**：全部发布事项对比、源码与 npm 产物核对、兼容改造清单、U0–U4 执行设计、验收/回滚/观察期计划。

**后续实施保持的既定决策**：官方自动化任务不接入；interval 最小 300s；14 业务域 + bus；Task/Campaign/Run 定义不变；SQLite WAL 多进程架构不变；scope fail-closed、approval effect 幂等、模型无权自行确认漏洞；反馈本地化；保留“超过 7 天且不在最新 2 万行内才删除”的清理口径。

**独立治理专项**：FTS、大列表虚拟化、知识质量治理、Campaign 3 预算决策、存量漏洞人工提交由 [27 号业务与容量计划](27-business-quality-and-capacity-plan-2026-09-30.md)承接。**不绑定版本不等于全部等升级后**：建议旧链关账后、0.2.0 切换前先做知识列表最小修复、提交分诊/SOP、C3 决策包与知识抽样；完整分页/轮询、FTS 扩展和按需虚拟化分批后置。它们不整体成为升级门禁；候选封存后如纳入新的代码/配置变更，须重新验收封存，详见 27 号 §10。

## 5. 源码与产物深查：升级的实质风险

### 5.1 Session 仍为 V4，但旧升级工具不支持 V4→V4

上游 `packages/core/session/src/types.ts` 定义 `SESSION_FORMAT_VERSION = 4`。rc.2 新问答持久化说明明确为 `same-version`：新增 `user-question-reply` 来源，不新增 Session header 版本。

**本地已定位阻断点：**

| 位置 | 当前逻辑 | 0.2.0 风险 | 必须改成的行为 |
|---|---|---|---|
| `dsh-upgrade.sh:24` / `dsh-upgrade-release.py:32` | 只允许 0.1.2→0.1.5、0.1.5→0.1.7 | 新组合直接拒绝 | 增加精确 `0.1.7-rc.2→0.2.0-rc.2`，未知组合仍拒绝 |
| `dsh-upgrade-candidate.py:14` | target 白名单两版 | 候选无法构建 | 新版受控配置与插件 pins；不能仅放开通配版本 |
| `dsh-upgrade-release.py:51` | target 恰为 0.1.7 才用 `session.v4.jsonl*`，否则 V3 | 加白名单后仍可能错误选择 V3 | 建立版本→会话格式能力表，不用“非 0.1.7 就是 V3” |
| `dsh-upgrade-release.py:298–334` | 运行迁移、要求目标日志不存在、拷贝新代次文件 | 源已含 V4，将拒绝覆盖或错误发布 | **增加同格式分支**：副本全量读回、记录清单/摘要、保留原文件，不创建第二套 V4 |
| `dsh-session-*` / `dsh-upgrade-session-*` | 存在旧版/目标等值分支 | 读回、数量、压缩/目录格式断言可能沿用跨代假设 | 全量检索版本判断，统一适配 V4→V4 |
| `dsh-upgrade-invariants.py` | 白名单含旧迁移/注册/索引变化 | 过宽白名单可掩盖本次错误导入或日志改写 | 为 0.2.0 单设白名单；同格式升级不默认允许旧 settings 改名或日志转换 |

实施时区分三种数据：①封存候选的程序/插件；②新鲜冻结点的业务状态；③隔离预演产生的数据。**不得把预演产生的新会话或旧业务快照作为生产状态覆盖回去。**

Session 门禁：

1. 统计活动/归档/压缩/分叉会话和 legacy-only 异常；旧 V3 文件与对应 V4 共存不能重复计数。
2. 同一份冻结副本用 0.1.7 和 0.2.0 全量读取，各有效会话 100% 成功；对比 id、父子关系、inheritedEventCount、事件顺序与数量、工具记录和费用投影。
3. 在新版本副本续写后，再用旧版本读回新增事件。**相同 header 版本不能替代反向兼容验证**。
4. 对未闭合尾部，区分纯读与会触发修复的写打开；自动修复必须形成逐会话 diff，不笼统允许所有日志变化。
5. 新问答来源、恢复后的 synthetic tool/result、bill 缓存重折叠分别覆盖；默认禁用 timed 也不能省略基础日志回归。
6. 主动制造版本/源目录/摘要不匹配，确认发布在交换根之前拒绝。

### 5.5 工具失败恢复：修复历史，不承诺自动重试安全

rc.1 在每个 live step 中引入 `ToolCallRecovery`，异常时先补足未提交结果的 `tool/result` 再关闭 step；已开始但无持久结果标为 `TOOL_OUTCOME_UNKNOWN`，未开始则 `TOOL_NOT_STARTED`。同一机制用于中断恢复和 fork seed。

必须验证三条边界：

1. **Session 结果与业务结果不同**：synthetic error 不得被 `exec.run.completed`/task.finished 误当成真实执行成功；实际 Run、FGS 和结果目录是核实副作用的重要依据。
2. **跨层重试不重复**：工具恢复 + LLM retry + failover + worker resume 不能叠加成重复扫描、重复登记、重复 approval effect。重放写命令核对 operation/idempotency key，未知副作用先读取外部状态。
3. **并发与崩溃不串线**：两会话并行、fork、工具执行后 worker 退出、结果落盘后回复丢失，都应保持 session_id/run_id/task_id 关联与可追溯性。

隔离 fixture 建议设置外部计数器：首次写计数已发生但返回中断，续聊后计数仍为 1；只读工具可以按预定策略重试；未知结果不得被模型直接宣布 verified。

上游变化不能自动修复已有闭合历史中的所有悬空结果。历史异常先识别、记录和单独处置，不在升级时批量伪造成功结果。

### 5.6 异步问答：本轮不启用 timed

精确包名是 `@deepseek-ai/dsh-tool-ask-user`。随附 preset 默认 legacy；timed 配置位于 **preset 的 `config.plugins` 中对应条目**，不是任意顶层 patch 行。

```yaml
# 仅示意后续试验的嵌套插件条目，本轮不应用
- id: tool-ask-user
  name: '@deepseek-ai/dsh-tool-ask-user'
  config:
    mode: timed
    timeout: 120
```

源码契约：正数超时返回 pending；`timeout: -1` 无限等待；推荐选项预选不代表提交；迟到答案经 `user-question-reply` 来源进入消息/inbox，按 callId 配对；活跃的受委派 subagent 被拒绝。进程独立的 headless worker 可能是运行时 root，**不能只靠该 subagent 限制保证 worker 不提问**。

本轮：保留 legacy schema 和现有 approval/task_block 流程；headless 没有 answerer 时不能无限挂住或超时后擅自推进。未来 timed 单独试点时必须覆盖：超时未答、迟到答、双 Client 同时答、刷新重启、取消、队列消息、worker 生命周期及旧版读回。普通回答不得直接执行 scope 变更、预算扩展、Campaign 升档或漏洞提交；这些仍走原审批契约。

| 指标 | 方法与建议门槛 |

## 10. 备份、回滚与异常处置

### 10.1 完整恢复点

沿用现有 freeze-config 对全部 roots 的定义，U0 重新核验路径与写者。至少包含：

- app、app/profile package.json、全部 lock 与核心/第三方插件、补丁后的实际文件；
- home/profile/CLI patch、settings 历史文件、7 preset、必要的运行环境配置；
- DSH 会话、归档/压缩日志、workspace 元数据及投影缓存的恢复策略；
- 全部领域 SQLite、计费库及 WAL 一致性状态、audit/outbox/idempotency；
- results/Run 证据、FGS、报告、知识/vault 和其他 freeze-config 定义的可变目录；
- 服务 unit/drop-in、工具版本、文件权限/UID/GID/软链接关系。

SQLite 必须在写者冻结后形成一致备份或使用现有受控备份机制；不能只复制主 db 文件而漏掉仍有效的 WAL。缓存可重建与不可丢业务数据分别标注；不得因为“只是缓存”而直接删除含费用/归因状态的未知表。

磁盘按 **冻结点 + next + rollback + 隔离恢复副本 + 新版观察期增量 + 安全余量** 实测估算，核查跨文件系统限制。上次 824G 可用是旧数据，不直接写入此次容量结论。

### 10.2 触发回滚/停止的条件

- 登录门失效、scope/approval fail-open、发现非预期业务日志外传；
- 会话不可读、canonical 日志不可解释改写、业务表丢失、非白名单不变量差异；
- 模型无法解析/路由错误、worker 无法运行、计费/预算归因中断；
- 持续崩溃、锁失效、重复任务/副作用、调度死锁；
- seal/工具/配置与验收对象不一致。

纯桌面文案变化、既存且已登记的 kbList 错误不自动触发全量回滚，但不能掩盖新回归。

### 10.3 两种回滚阶段

| 阶段 | 处理 | 数据要求 |
|---|---|---|
| 写者尚未恢复 | 保持冻结；保全 rc.2 状态/日志；执行现有发布回滚协议，四根回到完整 0.1.7 恢复点；旧版维护验收通过后恢复写者 | 业务应无新写入；记录所有维护差异，目标业务 RPO=0 |
| 写者已恢复 | 先再次冻结；捕获新版一致性点，运行 `preserve_after_resume`；保全新会话/Run/库/费用/证据；依据已预演的兼容性决定恢复与对账 | **不能直接覆盖旧快照后声称无损**；无法直接并入旧版的新事件留在隔离副本，记录真实 RPO/未恢复项 |

“还原 npm 包版本”不是回滚。V4 同版本也不允许假设所有新增 projection/source 均向后兼容。恢复后必须验 0.1.7 实际包版本、15 域、配置/preset、全量会话、数据库、模型/费用和服务锁。

### 10.4 上次失败教训如何落实

| 上次事实 | 此次必须有的工程约束 |
|---|---|
