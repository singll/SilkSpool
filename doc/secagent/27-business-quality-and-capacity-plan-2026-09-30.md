## 1. 结论：独立立项，分前后两段，不整体等待 0.2.0

**新开本 27 号专项文档，承接跨版本的业务与容量工作；26 号只管运行时升级。** 25 号已有大数据治理方向，但它和学习/漏洞/Campaign 文档尚未构成一份统一、可执行、带优先级的剩余工作计划。本文件补齐缺口，不重写已经完成的历史方案。

推荐顺序：

1. **现在、旧升级关账期间**：完成方案、清单模板和离线测试设计；使用关账操作最终产出的基线，避免另开写者/冻结/重建干扰验收。
2. **0.1.7 关账后，0.2.0 生产切换前**：先做知识列表最小修复、提交积压分诊与 SOP、Campaign 3 成本核对及处置决策、知识质量小样本基线。它们直接影响可用性、成本和成果流转，不应等所有性能改造完成。
3. **与 0.2.0 离线准备并行**：实现上述小改动的独立批次、制作 FTS/分页基准，不在两个分支同时改同一插件。已合入的业务修复必须进入 0.2.0 最终候选。
4. **0.2.0 切换和观察期间**：暂停非必要 schema、检索排序、全局 UI 和清理策略发布；既有批准范围内的日常运营可继续，所有新增数据纳入升级对账。
5. **0.2.0 关账后**：依次完成跨列表分页、轮询和缓存；按实测瓶颈扩大 FTS；虚拟滚动最后按需实施；知识质量的评分/排序变更单独实验发布。

“非版本绑定”意味着有独立里程碑，不意味着一律后置，也不意味着它们都成为 0.2.0 的硬依赖。**提交全清、平台 accepted、Campaign 3 获批续费、FTS 上线、虚拟滚动完成，均不应成为升级放行条件。**

### 2.2 四个容易误判的点

- **知识已有 FTS**：后端已建 `exp_fts`（external-content）和 `kb_fts`（standalone）。待做的是查询策略优化和资产/漏洞/事实等新增索引，不是从零搭建全文检索。
- **列表缺数据不靠虚拟滚动修复**：后端或 RPC 只取前 200/500 条时，前端虚拟化只能更快显示不完整数据。必须先完成服务端筛选、分页、total 与截断语义。
- **inconclusive 不等于分类 bug**：`exec.run.completed exit=0` 没有判定只记 `run_ok_no_verdict`；任务完成、候选被拒绝不自动等于有效阴性。不得为改善面板数字把它们批量改成 valid_clean。
- **业务闭环不是未建设**：提交队列、草稿、remote_id、预算审批、知识 revision/eval/publish 已存在。缺的是运营责任、当前队列处置、结果验证与部分查询可用性，不应再造一套系统。

| 工作 | 当前判断 | 紧急度 | 0.2.0 前做什么 | 0.2.0 后做什么 | 是否阻断升级 |
|---|---|---|---|---|---|---|
| 提交积压 | 工具齐、运营计划不完整；有历史积压 | **E1，业务优先** | 全量分诊、责任人/下一动作、准备首批审校材料，按已有权限开展运营 | 持续跟进平台反馈、复验和沉淀 | 不要求全清；需明确数据保全与操作者 |

| FTS 扩展/优化 | 部分已有，部分方向级，缺选型/回填/验收细节 | **E2/E3** | 查询计划+语料基准、知识 LIKE 策略研究；必要时先做窄范围正确性修复 | 热点优先索引、回填、影子比对与启用 | 无测得瓶颈不阻断 |

## 5. 工作流 D：存量漏洞提交与运营闭环

### 5.1 目标与复用边界

目标是让每个当前 confirmed 未提交项有明确去向，产生可核验的真实提交/阻塞结果；不以清空队列或提高 accepted 数作短期工程验收。

现有能力：`vuln_submission_queue`、`vuln_dedup_check`、report 域草稿命令、任务 review/submit 流程、`vuln_submit` 的 remote_id/vendor_status/bounty、看板待提交 KPI。**`vuln_submit` 是平台提交后的本地记账，不负责代替平台发送。** 当前 remote_id 可空，本地状态变化本身不能证明真实提交成功。

### 5.2 D0：全量分诊与责任登记（升级前）

1. 以关账后的只读基线取得所有 confirmed 且 submitted_at 为空的信号；队列 SQL 有 limit，不能拿默认 50 行当全量。超出上限时使用受控全量导出/已有分页查询对账，原始 SQL仅用于只读核查。
2. 对照平台已有工单，排除“实际已提交但未记账”；核实 finding→Program→证据/报告关联，标注重复、过期、需补证据、需确认规则等。
3. 每项登记：finding_id、Program、严重度、平台、创建/确认时间、证据日期、报告引用、分诊结果、负责人、审校人、下一动作、计划日期、阻塞原因、平台工单/回执引用。
4. 先用现有 Task 和 report/证据目录承载流程备注，不新增 Finding 状态或新业务域；若缺结构化负责人字段，再评估最小列演进，不能在备注中另建不可对账的状态机。
5. 优先处理高风险、授权/证据时效短、材料齐全者；同优先级再按等待时间。现有队列实际按 severity DESC、created_at ASC 排序，是同严重度最老优先；“年龄升序”的旧注释不能替代 SQL 语义。

**验收**：全量计数与查询 total 一致；每项有责任和下一步；历史 44/9 不被硬编码为目标数量；敏感证据不写入公开计划或 commit。

### 5.3 D1：人工提交 SOP（本次新增方案）

| 步骤 | 行为 | 输出/失败处理 |
|---|---|---|
| 资格复核 | 对照当前授权、平台接收范围/规则、目标和证据时效；必要复验走现有 scope/exec | 不满足则任务 blocked + 原因，不为了清 backlog 伪造提交 |
| 技术审校 | 复核复现、影响、正负对照、机器证据/胶囊；旧 confirmed 不默认满足最新证据标准 | 明确“可提交/补证据/疑似重复/不再有效”；错误判定通过合法域命令修正并留痕 |
| 材料准备 | 使用 report_draft_submission，整理最小必要请求/响应、影响说明、修复建议，凭据脱敏 | 保存草稿版本/摘要、finding 与证据引用 |
| 人工批准发送 | 指定有平台权限的操作者确认最终材料与目标平台 | 规划和技术审校不自动授权本轮发送；待执行时按实际授权操作 |
| 实际提交 | 操作者通过既有平台工作流发送 | 成功保存工单号/URL/时间与受限回执；超时先查平台，防重复提交 |
| 本地记账 | 平台成功后执行 vuln_submit，记录 remote_id/platform/submission_url；任务写完成依据 | 若本地记账失败，标“平台成功、待对账”，先补记而非重复发 |
| 平台裁决回流 | accepted/rejected/duplicate 等真实结果回填 vendor_status，附回执 | 回流学习与策略；平台未回复不得自行标 accepted |

**建议 SLA（待运营负责人采纳，并非已有规则）**：分诊后 high/critical 1 个工作日内审校；medium 3 个工作日；其余 5 个工作日。材料通过后下一个约定提交窗口处理；blocked 每周复核一次。SLA 从“当前材料已就绪/分诊时刻”计时；若需要“确认后时长”，必须有可信 confirmed 时间，不能直接用 created_at 代替。

首批选 3–5 条材料完整项验证流程；量不足则全量，避免一次处理历史全部积压。验收是每项有可核验结果与下一步，平台结果不可作为必须达成的外部指标。

### 5.4 D2：运营硬化（独立小批次，视需要升级前/后）

- 补“待提交总量/已就绪/待审校/阻塞/已提交待裁决”投影；流程阶段属于 task/report 派生视图，不私加 Finding 终态。
- 本地 submitted 且无远端回执列为数据质量告警；存量先对账，不能直接重置或强行补 remote_id。
- 若未来把新提交 remote_id 改必填，要支持平台无标准 ID 时的替代回执，并评估历史兼容，先写契约再实施。
- 记录本周审校/真实提交/裁决回流、就绪等待时间、重复发送数；重复发送目标 0；不把草稿数计为提交成果。

## 6. 工作流 C：Campaign 3 预算与退出/续期决策

### 6.1 先解释花费，再决定追加

当前存在三种不同约束：Campaign budget/window、Program 预算闸、LLM 供给。09-30 修复的 verify 连败/回升也与资金决策不同。**余额不足不等于算法失败，供给可用也不意味着必须继续花费。**

C0 决策包必须包含：

- 当前 id/name/status/autonomy、Program/目标与授权、budget_tokens、budget_window_days、审批与 checkpoint。
- `campaign_get.window_usage` 的窗口用量、累计 spent_tokens、可用余额、正在运行任务的潜在增量；分别标注 token 与货币成本，不能混比。
- 近一个预算窗口及全生命周期按 task_class/campaign_role/strategy/失败原因的请求、token、Run、任务结果、有效候选/verified/可提交成果。
- 已修问题造成的重复 param、超时/重启、无效派生占比；修复后的样本独立列，不能用混合历史得出新策略收益。
- 当前 queued/blocked/running、待审预算申请、可复用证据和还值得做的具体小目标。

`campaign_get` 只给最近 50 decisions/100 active tasks/20 checkpoints，不能直接当全量成本报告；使用分页/聚合与原始台账核对。99.997% 是历史值；窗口滚动后余额可能恢复，不得直接按旧值生成续费审批。

### 6.2 推荐决策树

| 条件 | 推荐动作 | 需要注意 |
|---|---|---|
| 授权失效、目标不再成立 | 不新增执行，准备归档/终止处置 | 仍保全全部证据；通过现有域命令执行 |
| 已有高价值成果但尚未提交/复核 | 优先完成 D 流程，收缩新增探索 | 提交/审校投入单列，不等同继续广泛 recon |
| 问题已修且剩余目标明确、有近期可验证收益 | 申请**一次小额、有限目标续期试运行** | 由人工裁决；限定任务数/时长/预算，不自动无限叠加 |
| 主要成本仍为重复/基础设施失败、无明确下一目标 | 推荐不追加，保持受控状态或按合法状态转换暂停，出归档决策 | 不为制造 running 数量而恢复 |
| 信息不足或无人决策 | 不自动新增预算；登记负责人、截止日、待补证据 | 不能假设“不批预算=永久停派”，窗口回落可能触发自动恢复；如需明确停派须执行合法状态命令 |

有限续期预算建议由下一批任务估算决定：`本批预计任务数 × 修复后同类 token P90 + 有界余量`，同时记录最大运行时长和货币成本估算。样本不足则先离线估算/更小批；不能使用任意固定百万 token 作为默认。

现有 `campaign-budget-extend` 要求正整数增量、原预算基准、通常≥80%水位（reviewing 豁免）、单次增量≤当前预算×2。该技术上限不是推荐投入。批准后核对 approval effect applied、预算增量和重复执行幂等，再观察下一批；本轮仅制定规则，不提交审批或增加预算。

### 6.3 停止、归档与回滚边界

当前 `campaign_pause` 只接受 active，`campaign_resume` 只接受 paused，不能向 reviewing 直接发送 resume。`campaign_archive` 会取消其取到的 queued 子任务，在跑的允许跑完；当前实现查询 queued 最多 200 行，因此**不能只看归档成功就宣称所有队列已清**。归档前核对总数、未决草稿与 blocked/running，超过窗口时另行分页处置/修复，再逐项验收；不直接 SQL 改状态。

预算已经消耗无法回滚。回退应停止后续派发、保存结算与证据；不能用调低 spent_tokens 或重置历史来“恢复预算”。选择归档时记录目标完成度、遗留成果、未完成任务去向，防止归档丢掉提交价值。

**C 流程完成定义**：产生可审查决策包并有明确“暂不追加/有限续期/归档”等人类处置；执行后账与状态一致。如果还等待决定，任务状态写“待决策”，不写“已完成”，但不因此阻塞 0.2.0 技术升级。

## 7. 工作流 K：知识可用性与质量治理

### 7.1 K0：先修 kbList 的最小闭环（推荐升级前）

本地代码明确：dashboard `kbList` 总传 `q`，而 know.kb_list schema 没有 q；领域处理器最多先取 500，bus 再切 limit/offset；UI 固定 RPC 后客户端过滤。**不是完全没有分页机制，而是分页被前 500 候选和前端固定窗口限制。** `meta.counts` 经 bus 展平为 counts，不能误把它诊断为统计字段丢失。

分两步实施：

**K0a 最小恢复（0.5–1 天）**：RPC 不再向 kb_list 传不支持的 q；保留本页过滤时明确标“当前页筛选”，返回 total/limit/offset 和截断提示；恢复无筛选列表，不谎称全库搜索。新增真实 schema→bus→RPC 契约，覆盖空 q、非空输入处理、列表正常返回。不能只改 mock 让它接受非法 q。

**K0b 全量可用（约 1–2 天，与 P 流程合并）**：在 know.kb_list 正式定义元数据 q（建议标题/source_url，精确字段在实现前固化）、category/status、limit/offset；过滤在 SQL 分页前，稳定排序以 id 收尾；list/count 同谓词；处理器标 `meta.paged: true` 防总线二次切片；RPC 保留分页元数据，UI 改服务端过滤与翻页。

列表浏览与 kb_search 的正文/语义相关性检索保持不同语义；不把全文 top-k 结果的数量冒充全库命中总数。K0b 若赶不上候选封存，先交 K0a；不要为了“一次做全”把确定性缺陷拖到虚拟化之后。

验收数据必须超过 500 条，覆盖第 501 条、翻到末页、同标题排序、过滤后 offset 归零、归档/生命周期排除、total 与可见集合一致；本地 420 条历史数据不足以证明上限问题已经解决。

### 7.2 K1：分层审计，而非批量清洗（升级前可完成）

抽样建议：选 3 类代表任务（recon/verify/review），覆盖不同 Program、最近修复前后、不同模型/渠道与正/负/未知结果。每层先取最多 10 条，初始 30–60 条；样本不足如实报告，不能为了凑数引入模型伪造真值。

每个样本沿链追踪：任务目标→检索 q→候选/实际曝光→采用或未采用原因→artifact/revision→执行证据→判定 episode→score→后续 planner 使用。记录无法关联的断点；优先复用 know_learning_trace、know_retrieval_explain、know_learning_status 和现有曝光/采用/episode 表。

| 指标 | 建议口径 | 避免的误读 |
|---|---|---|
| 检索覆盖 | 具备检索适用条件的任务中，实际发生检索的任务占比 | 所有任务都必须检索三次会造成无意义成本 |
| 可关联曝光 | 能关联 Program/Session/artifact 版本的实际展示事件 / 全部展示事件 | 查询命中不等于向模型展示 |
| 采用率 | 有采用证据的已曝光 artifact-task 对 / 可比较曝光对 | kb.uses 累计值不是采用分母 |
| 结果可归因率 | 能关联执行与证据的判定样本 / 待归因判定样本 | run 完成和 task 完成不能当多个独立检出成果 |
| 有效阴性/正例 | 依据 oracle/可信判定分层计数，模型自评单列 | rejected/exit 0 不自动转 valid_clean/confirmed |
| 成本效率 | 同类有效结果的 token/耗时/货币成本，说明样本量 | 跨不同模型/不同目标直接比总 token 得不出因果结论 |

分类规则沿用六类 outcome。先统计 inconclusive 的 reason_code：run_ok_no_verdict、task_done、truth_rejected、vuln_reject 等；只修有证据的丢失归因或错误分类。旧 episode 不原地覆写，修正通过 supersedes/消费者版本及去重规则处理；scores 重建不修改历史。

**完成定义**：形成“设计预期/已证实缺陷/证据不足”三类问题表，每个缺陷能定位到事件、接口和测试；不以 inconclusive 降到某比例为验收。

### 7.3 K2：检索与使用闭环的定向修复（小缺陷可前置，大调整后置）

候选修复按 K1 证据选择：实际检索未回执、采用未连 artifact、task/run/Program 关联缺失、过期/tainted/跨范围材料排序错误、重复事件重复计分、来源/版本不可追溯。43 号已修的 task_id/hit_matrix/候选验证、09-30 连败排除先回归，不重复开发。

只对实际使用落采用回执；刷新/重复读取不增加“成果”。知识正文中的指令保持不可信材料；发布仍走 revision→独立评测→审批→release；不恢复模型直写/自我晋升通道。

### 7.4 K3：对照评测与渐进发布（建议 0.2.0 关账后）

1. 固定 DSH/模型/provider/prompt/任务集合、预算和语料快照，先建立 baseline；模型更换另起实验，不能同时升级 DSH 和检索后把收益全部归给知识治理。
2. 建初始检索集建议 30–50 个真实代表 query，标注相关文献、有效期与范围；覆盖中文、多词、域名/路径、无命中、提示注入材料和错误文献。
3. 对比 baseline、候选检索/排序、无知识参考三组；必要时重复运行以估计模型波动。至少记录 Recall@k、误相关/越域命中、证据支持率、有效判定与成本；top-k 相关性需有人类/可信 fixture 标注。
4. 使用现有 eval_run_candidate 与 revision 评测/发布契约，不再造一套评分器或把检索测试集直接注入待评任务答案。
5. 先单 Program 或单类任务小批启用；新版本发布绑定内容摘要、适用范围与评测结果。出现越域、证据误用、无收益且成本明显上升，撤回 release/恢复旧排序，不删除原始记录。

建议性能/质量门槛在 K1 后预登记：关键安全负例零放行，标注集关键相关材料不能丢失，Recall@k 不低于基线；成本涨幅超过 20% 必须有明确质量收益说明。不能将小样本改善写成全系统确定收益。

## 8. 工作流 F：FTS 与后端容量优化

### 8.1 现状与实施顺序

25 号 S0 中的 outbox 清理、ledger 截断修复、部分 LIMIT 与索引已有完成记录；本轮核查也看到 assets/endpoint/findings 的相关索引。**先验部署一致性与热点，再继续遗漏项**，不重新全量跑清理或建重复索引。

建议顺序：**分页与索引利用 → 知识现有 FTS 查询策略 → 资产热点 FTS → 按需漏洞/事实 FTS → 向量索引/ANN（仅规模证据成立）**。

知识现有 `ftsSearchKb`：FTS MATCH 后仍无条件 LIKE title/body；LIKE 虽带结果 LIMIT，却不保证扫描成本有界。`kb_search` 先固定候选参数 20、再遍历全部 embeddings；不能认为接口接受 limit=500 就能找遍全库。优化必须区分“完整列表检索”与“近似/限量相关性检索”。

### 8.2 F0：离线基准与选型（可在升级前）

从一致性副本生成脱敏/合成测试数据，分别测当前规模、2 倍和 5 倍；记录 query、返回 ID、SQL 计划、扫描/耗时、事件循环延迟、内存与写入代价。至少 30 类 query，覆盖汉字、空格、短词、域名点号、路径斜杠、CVE 编号、引号、无命中和高频词。

- 明确查询语义：精确域名/ID 优先 B-tree；前缀和全文 token 匹配不同；需要任意子串时 unicode61 不等价于原 LIKE。
- 中文分词与域名拆分须实测；选择 trigram 必须确认目标 SQLite 支持及短于三个字符的回退行为。不预设“一开 FTS5 中文就正确”。
- 用户查询经参数绑定和字面量转义，不把输入直接当 MATCH 表达式；通配符/引号/超长词有明确策略。
- 只有计数/查询语义稳定后定指标。建议 P95≤300ms、相比旧版热点显著改善且相关结果不退化；若原查询已满足，不为指标而扩大工程范围。

### 8.3 F1：先优化已有知识 FTS

建议采用 FTS 取候选→按领域可见性/生命周期过滤→不足时有界候选回退→必要的向量融合。**“不足”按过滤后的有效命中数计算**，不能让前 20 条全是归档材料后就报告无知识。

LIKE 回退需限定候选范围/正文片段/工作预算，并报告 fallback/truncated；不能仅加 LIMIT 就宣称 CPU 有界。全向量扫描是否替换先看实测；小库保持简单实现，优先缓存带版本的 embedding 集合和避免重复嵌入查询。缓存必须对正文/revision/lifecycle/范围变更失效。

保证已有 standalone kb_fts 与正文文件/metadata 的同步。**kb_docs 没有 body 列，不能直接把 kb_fts 改为 external-content(kb_docs.body)。** 新正文/删除/归档/重验与索引、向量更新的原子性/失败补偿按已有域契约处理。

### 8.4 F2：新增域 FTS 的工程方案（升级后按热点推进）

| 域 | 首选范围 | 设计注意 |
|---|---|---|
| asset | host/必要技术关键词 | host 与 fingerprints 为不同关系；技术关键词聚合须确定行粒度和触活/删除更新机制，不能靠一个不匹配的 content 表 |
| vuln | title/host/url | 状态/Program/信号面过滤由业务表决定；索引不包含凭据/不必要原始证据 |
| fact | summary/fact_key，正文另评估 | TTL、archived/timeline 可见域一致，不能索引查到而列表隐藏时绕过权限 |
| endpoint/task | 暂按精确/前缀/普通分页优化 | 仅在实测证实热点且前三类完成后立项 |

实施切片：

1. 明确主表稳定 id 与索引内容、schema 版本和最小触发器/事务维护方式；跨文件正文保持 standalone 策略。
2. 在恢复副本测试建表/分块回填、读写并发、失败续跑、磁盘峰值；业务真相源始终是原表/文件。
3. 短维护窗口或受控写入策略完成初始一致点；回填期新增/更新/删除通过触发器或增量队列追平，不能漏掉并发写入。
4. 影子查询比较新旧结果、可见域和 count，使用校验/重建命令验证索引内容，不以“表存在/行数相等”替代正确性。
5. 开关按域启用；主路径失败时显式告警并回退旧查询；保留旧查询至少一个验收周期。
6. 回退先关闭新读取，保留原表/备份；派生索引可随后重建，不整库还原覆盖上线后业务写入。

**验收**：导入/更新/删除/重验/归档/恢复/重放不漏不重；恶意或复杂查询不崩；匹配语义和 total 有说明；范围过滤不回退；对性能、写入成本、磁盘和恢复时间都有结果。

## 9. 工作流 P：分页、轮询、缓存与按需虚拟化

### 9.1 P1 服务端可见性先行

沿用现有 bus `rows/total/limit/offset` 和 `meta.paged`，不引入第二套分页 envelope。服务端 q/filter 后再分页；list/count 使用同一范围与生命周期谓词；确定性排序以稳定 id 收尾；换筛选回到第一页；并发变动时显式刷新，不保证跨时刻总数恒定。

优先视图：**知识（配合 K0）→任务/执行历史→审批/报告→资产族**；具体再按实际使用量调整。只修必须可见的数据，不在同批重构整个安全中心。

必测：超过 200/500/资产族 300 的边界、末页、空页/删除末项、筛选跨页、相同时间排序、错误重试、总线二次分页、权限过滤后计数一致。大 offset 确有瓶颈时再设计游标；升级前不同时变更全体消费者协议。

### 9.2 P2 轮询与缓存（建议 0.2.0 关账后）

源码共享 useRpc/usePagedQuery 使用 setInterval；应在共享层治理但先只挂一两个视图验证，避免全站故障。

- hidden 页面暂停非必要轮询、未激活 tab 不轮询；恢复可见只触发一次刷新，防所有端点同时突发。
- 同 endpoint+规范化 payload 去重，在途请求不叠加；查询参数变化加序号/取消，旧响应不得覆盖新筛选结果。
- 使用者卸载及时释放 timer；出错保留上次数据并标注 stale/错误，不用空列表掩盖故障。
- 稳定统计 60s 左右、运行任务更快的建议频率由基准定；人工写操作成功触发关联失效。暂停前端轮询不暂停服务端 scheduler/审批执行。
- 缓存键包含 Program/过滤/范围等可见性维度；写入/状态迁移/权限变化可失效；低开销读查询优先，不跨用户复用敏感结果。

**验收**：隐藏/未激活时非必要请求为 0；在途同键最多 1；页面恢复不重复 burst；写后能看到结果；断网/重连/切页不显示他域数据；实际 RPC 数/CPU/P95 对比有改善。

### 9.3 P3 虚拟滚动的启动条件与方案

**不默认必做。** 先分页成 50–100 行，若目标设备上首屏、滚动和内存已达标，暂缓并保留基准；不要为了“完成 S2”强上复杂度。

建议启动条件：有业务确需连续浏览数百/数千行，且性能分析确认渲染 DOM 是主瓶颈，而非 RPC/SQL/网络。先对资产列表或任务历史中实测更差的一个视图试点；长会话属于 DSH 上游面，不能直接拿业务表格方案替换。

方案要求：

1. 固定高度行优先；详情展开移到现有抽屉。若必须可变高，使用可靠测量/缓存和尺寸变化重算，不预估永久不变。
2. 稳定 row id、有限 overscan、视口外占位；筛选/排序后滚动归位；“跳到 finding/task”先服务端定位再定位页/行，不依赖 DOM 全存在。
3. 中文输入、键盘上下选择/焦点、读屏语义、工具提示、表头、选中项和费用/状态刷新均测试；浏览器页内查找/打印受虚拟化影响，提供服务端搜索和导出说明。
4. 页面级开关回退普通分页表格；不把所有 UI 核心一次换成新表格库。
5. 在固定设备/数据集测首次渲染、连续滚动、DOM 数、长任务与 RSS；建议一次挂载行数受视口+overscan 有界控制，不能仅以“看起来更顺”验收。

**完成定义**：与普通分页功能等价、明确可访问性和查找语义、测得性能收益；若无收益，保留普通分页并记录不实施结论，也可完成该项评估。

### 11.1 通用验收与恢复

- 代码批次仅跑受影响的领域/RPC/UI/共享总线契约；修改共享分页/轮询时覆盖所有直接消费者。生产部署仍需现有 accept/data-quality，实际数量记录，不把旧 PASS 当新结果。
- 所有数据库/索引写操作先有一致恢复点；原业务事实不以整库回退抹去上线后写入，优先关读取开关/恢复旧代码/重建派生索引。
- D/C 是业务状态动作，不是纯代码回滚：已经发送、平台已裁决、预算已消耗的事实不能撤销伪造；纠错走补记/事件/合法状态迁移。
- 实施期间所有远程操作使用 PATH 中的 spool；本次未执行任何远程动作。
- 每包留实际日期、代码 commit、部署 SHA、测试结果、恢复点、未解决项；当前结果写 PROGRESS，正式行为回填 02/05/07/09/12/15/16 与相关资产/事实域。

### 11.2 独立关账，不绑整份计划一次完成

G/K0/D/C/P/F/K3 各包独立验收；D 的“持续平台跟进”可转日常运营，C 的“待人类决定”明确保留，P3 可因无瓶颈而关闭评估。所有交付完成/转常驻治理/明确取消后本 27 号文档归档；不要因为某项无限期跟进让 25 或 26 永久无法关账。
