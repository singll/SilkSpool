## 1. 核心判断与有效产出的定义

**目前 SilkSecAgent 已具备较完整的平台骨架，但还没有形成“可工作的业务请求 → 可检验假设 → 可信漏洞证据 → SRC 认可 → 策略改进”的稳定生产闭环。** 主要短板不是工具数量、资产总量、上下文长度或套餐是否花完，而是可测试业务面的形成、任务目标约束、判定真值、执行归因和学习应用。

当前不能说“系统从来没发现过漏洞”，也不能说“44 条 confirmed 只差提交”。44 条中有 28 条来自旧系统导入；31 条为 info/low；没有一条关联当前任务；30 条缺结构化复现步骤。它们需要重新审校。另一方面，当前自动编排体系的新增有效漏洞收益没有得到证明，生产数据支持优先整改而非继续放大吞吐。

### 1.1 唯一北极星与中间指标

北极星是：**授权项目内，独立复现、有明确安全影响、符合接收规则、去重后被 SRC 认可的漏洞产出，以及获得该产出的时间/成本。** 平台裁决存在等待周期，所以工程验收用可信中间指标判断链路是否工作，但不把中间指标冒充最终成果。

| 层次 | 准确定义 | 不足以证明它的现有数据 |
|---|---|---|
| 可测试业务面 | 目标在授权/接收范围；请求能正常到达业务；身份、对象、输入和正对照可用 | 域名数、200 数、`level=S`、URL 数 |
| 有效尝试 | 对具体请求与安全假设执行了有界测试，前置成立，有可追溯结果 | 启动工具、worker exit=0、任务 done |
| 已验证漏洞 | 原始证据支持违反安全属性；排除公开功能、登录页、WAF、网络伪影等反证 | 标记回显、长度相近、敏感正则、模型写 `verified` |
| 可提交漏洞 | 上述条件 + 当前项目接收资格 + 影响/复现材料完整 + 去重审校通过 | confirmed 状态、生成草稿 |
| 已提交漏洞 | 外部平台提交成功，有工单/可核验回执 | `vuln_submit` 的本地状态变更、提交任务 done |
| 平台认可漏洞 | 平台实际裁决 accepted；duplicate/not_rewarded 等另列 | Campaign Reviewer 的 `accepted` |

所有比例按同一 cohort（同一批输入/时间窗、项目、版本）计算。不能用当前噪声池存量作历史候选分母，也不能把一次执行的 run/task/finding 三条事件算三个成果。token、货币、耗时、人工审校时间分别记账。

### 1.2 本次证据等级

- **R：运行事实**——本次只读查询/文件元数据可见，带时间和统计口径。
- **C：代码确定性缺口**——定位现行函数、契约或调用链；关键规则已用本地合成输入复现。
- **H：待验证影响/设计风险**——代码或数据提示风险，但尚未做生产因果实验；不能写成已经发生。
- **S：已有能力/既有修复应保留**——不要重复建设，更不能为提速移除正确约束。

这是一份对全部主链路和支撑环节的逐项审查，不是形式化证明所有代码无遗漏。未做的目标复现、平台核单、压力测试和真实业务登录验证在 §14 明确列出。

## 3. “挖不到有效漏洞”的因果链

### 3.1 首要根因：把目录覆盖当成了可验证业务覆盖

资产域名多，但业务会话、请求体、对象归属、参数位置和成功正对照少。Planner 主要从 `host|class` 缺口出题，再让昂贵的 LLM worker 从零寻找入口。IDOR 没有双账号/对象、SQLi 没有有效输入、SSRF 没有可控服务端取址点时，派发类名不能创造测试前提。反复补参、伪端点和登录页比真正漏洞更容易占满队列。

### 3.2 第二根因：目标规格是说明文本，未成为执行约束

`goal_spec.vuln_classes/targets/stop_conditions/review_cadence_sec` 主要被保存/展示；通用 Planner 继续消费所有缺口，Supervisor 没有通用结构化停止条件执行器。C3 跑去枚举/补参是可预期结果。清理专项目标、发现专项目标、成果审校目标没有真正隔离。

### 3.3 第三根因：判断依据比提示词宣称的弱

提示词要求独立验证、正负对照、随机标记和业务影响；代码却能把普通回显、单次时延、公开邮箱判 verified。capsule 可由调用方提交 verdict，confirm 的非 capsule 证据路径主要检查存在性，Reviewer 还从文本正则取“验证成功”。这会制造假正例，也会把登录/网络阻塞或证据不足过早记成 false_positive。

### 3.4 第四根因：低收益输入被反复放大，失败与未知又压缩探索面

旧 authz_diff 用“两个响应很像”产生 high 候选；它不要求两种凭据真实不同、正对照成功或对象私有。后来按来源类别高拒绝率自动抑制，可能把修坏输入源的问题变成整类 IDOR 少看。另一方面，coverage 的 rejected/inconclusive 可以永久关闭 host×class，strategy attempted 也可能阻止重访；合理的网络失败不能获得正确的重试前提。

### 3.5 第五根因：执行和成果都缺统一归因

生产 findings.task_id 全空，学习 card/model/cost 全空；回收行也有 run_id 空洞。没有 attempt 级关系就无法区分“没有漏洞”“没有执行”“工具/身份不工作”“有结论但没入库”，更无法知道钱花在哪条可重复的方法上。

### 3.6 第六根因：自主学习的主要产物是记录，不是可执行改进

当前有 revision/eval/release、事实生命周期、向量/FTS、反馈桥等结构，应保留。但真实使用回执大量无法解析卡 ID，结果关联缺失，矩阵没有胜负样本，候选评测也没有真正运行候选知识的行为。继续增加文献、让 agent 多写总结，不能自动补齐这些断点。

### 3.7 第七根因：成果出口没有完成条件

提交任务完成并不要求外部工单。38 份草稿、15 次 done、0 submitted 是“内部任务闭环”和“外部成果闭环”脱节的直接证据。即使先修出口，也必须重新验证 44 条历史 confirmed 的质量，不能批量提交它们来制造成功指标。

### 3.8 第八根因：成本控制奖励了活跃度，而不是已验证进展

代码默认允许预算达阈值后自动提请并自动批准扩容；任务预算目前主要是收尾超支标记。大量失败/派生也会刷新 heartbeat，难以发现“持续工作但没有成果”。**套餐可用、服务 active、验收脚本 PASS 都是必要条件，均不是值得继续扩大探索的充分条件。**

## 4. 全链路的保留、收缩与改造边界

| 环节/模块 | 是否需要 | 当前应保留 | 必须改进的产出契约 |
|---|---|---|---|
| 项目/授权/接收规则（scope/approval） | 必须 | fail-closed、审批 effect 幂等、工作区归属 | 官方接收规则与时效进入准入；审批批准≠实际 applied；集团归属≠平台接收 |
| 资产收集/指纹（asset、CT/FOFA/DNS） | 必须，但有界 | 多源发现、去重、分级、变化雷达 | 输出新鲜、归属明确、可达的业务面；域名增量不直接触发全类别扫描 |
| HTTP 基线/代理（exec/proxy） | 必须 | 执行留档、坏代理治理、QPS/范围机制 | 先辨正常业务/登录页/软404/代理错误，差分请求绑定稳定出口 |
| 爬取/流量/参数（endpoint、L2、浏览器） | 核心 | endpoint 图谱、Burp 导入、参数队列、browser 能力 | 请求模型保留 method/body/身份/对象/出处；把 JS 和真实业务流转成可用请求 |
| 身份与业务建模 | 当前最应加强 | credential 引用、auth_state、roles_seen | 两个自有测试身份、私有测试对象、登录健康、业务预期成为假设前置 |
| 假设与排序（rules/task） | 核心，需重构输入 | H1/H2/H3 分层、受控派生、预算和 scope 闸 | 对具体请求定义可证伪假设；目标规格强约束，按预计有效信息/成本排序 |
| 执行/调度（exec/task/worker） | 必须 | 独立 worker、deadline、回收、会话 nonce | claim/spawn/finish 成对，准确失败原因、真实预算预留、全局并发可控 |
| 覆盖/尝试/FGS（ledger/fgs/fact） | 需要，但减少重复写 | 持久检查点、证据链接、负知识、恢复能力 | 一个 attempt 真相源派生多视图；记录未知，不伪造阴性或覆盖完成 |
| 候选/机器验证（vuln/oracle） | 核心，优先修 | 候选与信号分层、反证、capsule、独立重放 | 真值来自执行证据与安全属性，来源/目标/版本强绑定 |
| 报告/提交（report/task/vuln） | 必须 | 草稿、提交队列、remote_id/vendor 回流 | 材料合格与真实发送分开；平台回执是完成依据 |
| 知识/学习（know/memcore/feedback） | 必须，先修闭环 | 四类知识分工、生命周期、评测审批发布 | 检索→采用→attempt→判定→版本收益可连接；按实际缺口补课 |
| 效果评测（eval） | 必须，需扩大真值面 | 独立 fixture、hidden 集、摘要锁定、配对实验 | 实际执行被评知识/策略；同时测漏报、误报、阻塞、成本和稳定性 |
| 面板/列表（dashboard/UI） | 为运营服务 | 现有工作台与分页协议 | 显示堵点、证据和下一动作；完整可见性优先于视觉/虚拟化 |

## 5. 逐环节问题清单：发现主链

优先级：**P0**=真值/目标/关键执行链不可信，修好前不扩大自动化；**P1**=直接提高有效业务面或发现能力；**P2**=有测量依据后优化周转/成本/容量。P0 是实施优先级，不表示本次已经修改或停掉生产。

## 7. 目标结构：围绕一次有效实验深化现有模块

### 7.1 保留领域边界，补齐一个贯穿链路的身份

保留现有领域插件、SQLite WAL、总线/outbox、工作区、候选/信号分层和revision/eval/release。当前没有证据支持先拆微服务、迁移向量数据库或重写平台。应在既有task/ledger/exec/vuln/know之间建立统一 **attempt_id**，并用不可变事件派生统计，而不是增加一套平行台账。

建议每次实验最少关联以下信息；具体落在哪张既有表/关联表由契约设计决定，避免把可变大正文塞入事件：

| 信息组 | 必需关联 | 用途 |
|---|---|---|
| 目标 | Program、接收规则版本、request_template_id/version、host/method、参数位置 | 证明测了哪个授权业务面 |
| 前置 | 身份/角色/租户引用、测试对象与归属、基线/出口健康、有效时间 | 区分“没有漏洞”与“实验不成立” |
| 假设 | hypothesis_id/version、安全属性、适用谓词、预期正反结果、停止条件 | 防止只派类别名和无限探索 |
| 知识 | artifact_kind/id、不可变revision/digest、采用角色、检索记录 | 将知识版本与实际行为连接 |
| 执行 | campaign/task/worker/session/exec_run、工具/模板/模型版本、lease/deadline | 定位未执行、回调丢失与版本差异 |
| 结论 | typed outcome、reason_code、oracle_id/version、verdict_id、可信来源 | 替代从自然语言猜真值 |
| 证据/成本 | manifest/digest、受限证据引用、token/request/耗时/费用与缺测标志 | 独立复现、结算及方法收益评估 |

凭据只保存受控引用；知识蒸馏去掉目标值和秘密。请求模板可包含机密字段占位符，执行时解析；报告只使用必要脱敏副本。

### 7.2 结果语义与阶段完成条件

实验状态建议统一为 `queued → prerequisites_check → running → judging → terminal`；依赖阻塞不占worker槽位。terminal结果与任务调度状态分开：

| 实验结果 | 证据含义 | 覆盖/学习/重试 |
|---|---|---|
| verified | 可信证据证明违反指定安全属性 | 进入独立复现与价值审校；技术正例，不自动accepted |
| valid_clean | 前置成立，当前条件下可靠反证 | 仅关闭该条件实验；记有效阴性与成本，条件变化重开 |
| inapplicable | 输入不满足该方法适用谓词 | 更新选题/适用规则；不记方法失败，不再原样重试 |
| blocked_auth / blocked_policy | 无可用身份或当前授权/接收前置不满足 | 转给前置责任人；前置变化后恢复，不能填clean |
| infra_error | 代理、工具、执行、OOB等未正常工作 | 有界技术重试或修复；不扣漏洞方法准确率 |
| inconclusive | 已执行但证据不足以肯定/否定 | 给出具体缺证与信息增益最高的下一步；预算耗尽停止 |
| cancelled / superseded | 主动终止或被新run替代 | 保留实耗；晚回调不可污染新实验 |

兼容已有finding.status/oracle三态时先加结构化reason和结果映射，不一次改坏所有消费者。`false_positive`是候选标签修正，`duplicate/out_of_policy`是分诊结果；它们都不自动等于实验valid_clean。

每阶段有单独DoD：资产收集完成要有解析/入库对账；请求采集完成要有健康可重放模板；参数任务完成要有逐项ack；验证完成要有typed verdict；出稿完成要有完整材料；提交完成要有外部回执；学习完成要有评测结果及采用反馈。一个exit=0不能替代这些条件。

### 7.3 事件与恢复契约

- claim和worker绑定在短事务/可恢复协议内完成；执行跨事务用lease和幂等键，不长时间占SQLite写锁。
- 一个attempt可以有多个run、多个观测和多个知识引用，但只有版本明确的当前判定；更正保留历史，不覆盖原证据。
- 完成、回收、取消、迟到费用都经过同一结算与事件应用器；outbox保证持久交付，投影按event_id/业务键幂等。
- ledger、FGS、facts、Reviewer、know_scores由结构化事实派生；低成本采集无需LLM重复撰写五份流水。
- 迁移仅补确定性关联。不能恢复的旧数据保留legacy/unknown，不用于训练当前自动化收益；重建投影可以回退，原始经历和证据不可丢弃。

## 8. 面向SRC的业务实验设计与选题顺序

### 8.1 各漏洞族的必要前置、充分证据和止损

下表是能力建设/验收清单，不代表已对真实目标完成验证。先根据项目接收规则及可用业务面选族，再决定工具；不按每host七类平均铺开。

| 漏洞族/业务面 | 实验必需前置 | 应证明的安全属性/主要反证 | 无收益时如何处理 |
|---|---|---|---|
| IDOR、水平/垂直/租户越权 | 两个自有测试主体、私有对象、合法访问正对照、权限预期 | 未授权主体读取/修改了其无权操作的对象；排除公开资源、共享关系、同账号及错误页 | 缺身份/归属转前置建设；真实clean只覆盖该权限关系，不关闭整host |
| SQLi | 正常业务请求、有效参数位置/类型、稳定基线 | 可重复的数据库求值影响；排除页面动态、WAF、代理/网络时延、参数校验错误 | 无数据库适用证据不长跑；不稳定先修基线，按预算停止 |
| XSS（反射/存储/DOM） | 真实输入→渲染路径、浏览器上下文、必要时两个测试用户 | 在预期受害者上下文发生受控执行及影响；排除编码、安全DOM sink、自操作和无跨用户影响 | 只有回显留传播事实；没有可执行路径不继续增加payload数量 |
| SSRF/服务端取址 | 可控取址功能、受控回调服务健康、请求关联 | 服务端发出非预期请求及可说明的权限边界影响；排除正常Webhook和浏览器请求 | OOB故障先阻塞；仅DNS回调与更强影响分层，不自动升高危 |
| 文件上传/下载/路径处理 | 合法测试文件、上传/访问流程、归属和存储策略 | 违反文件访问或执行/内容边界；排除正常公开文件、仅文件名回显、无实际访问 | 使用测试文件最小证明，不为证明影响访问无关私有文件 |
| 信息暴露/配置/N-day | 来源可信、部署/版本适用、项目接收规则 | 非公开敏感内容或可复现的实际受影响能力；排除通用banner/公开联系方式/过期样例 | 静态模板批量命中先分诊；无接收价值不占高预算验证位 |
| 认证、重置、绑定、邀请、OAuth/SSO | 自有账号、状态/回调/绑定关系与正常完整流程 | 身份/授权绑定违反预期；排除正常账号恢复和业务允许共享 | 缺业务模型先走流程建模；不靠关键字“登录”自动套类 |
| 金额/权益/次数/工作流逻辑 | 测试态或获准的可逆测试数据、预期业务约束 | 状态机或服务端校验缺失导致真实权限/权益差异 | 无安全影响只是功能异常；无法控制副作用则阻塞并转审查 |
| 并发/竞态/幂等 | 明确单次操作约束、可观测状态、获准的小规模并发预算 | 重复执行/并发导致约束破坏；与网络重复回包、最终一致性区分 | 从最小并发验证，不以压测替代逻辑证明 |
| GraphQL/批处理/导出/异步任务 | schema/真实请求、对象/字段/任务归属、完成回调 | 对象级/字段级/批任务权限属性；排除空结果、公开字段和正常异步状态 | 把方法用于具体请求形状；不要新增类名就宣称覆盖扩展 |

### 8.2 第一轮有效挖掘试点

建议先选**一个授权项目的一条有价值业务线**，以资产新鲜度、项目接收、账号可用和可观测性选择，暂不指定客户真实目标。起步收集约20–50份经过基线验证的请求模板，包含可用的查询/写入/API/登录态；这只是便于人工抽检的工程规模，不是发现漏洞的数量保证。

1. 用少量流量采集形成“业务动作—请求—身份—对象—权限”图；每个模板至少证明正常操作可复现。资产枚举只补该业务线缺失入口。
2. 对每条请求先判适用性，生成有前置的实验；每条假设可说明为什么有价值、怎样证明不成立、什么条件停止。
3. 先跑最有价值且可判定的一小批；每条都对账前置、执行、结论、费用。出现407/登录失效/空参数时优先解决同源阻塞，不继续增派同类任务。
4. 验证器通过受控正负样例后才用于真实授权请求；首次positive由独立执行/人工审校复核，不能由同一LLM自证。
5. 到预先登记的时间/成本窗口即复盘：没有漏洞但有可靠clean是可解释结果；大量unknown/未执行则是流程失败。根据具体瓶颈调整，不以“继续挖”自动续费。

## 9. 自主学习改造方案：让知识改变行动并能证明收益

### 9.1 学什么、从哪里学、学到哪里

| 输入 | 应产生的知识 | 不应产生的结论 |
|---|---|---|
| 成功验证及独立复现轨迹 | 适用前置、必要动作、判定/反证、最小证据、成本范围 | “该类都容易出洞”或含真实目标秘密的通用卡 |
| 合格阴性 | 已排除的具体假设、有效范围、可复用反证步骤 | 整个host/企业永久无此类漏洞 |
| 不适用/阻塞/故障 | 适用性约束、身份补齐方法、短期环境修复方案 | 方法准确率失败或不存在漏洞 |
| 平台反馈 | 接收资格、材料质量、重复根因、实际影响等级 | 把duplicate/policy拒收全部当技术误报 |
| 官方通告、公开研究、工具文档 | 带来源/日期/版本的参考及候选策略 | 未经评测直接成为全局可执行规则 |
| 检索miss/执行偏离 | 具体缺失概念或步骤、query改写/卡片缺口 | 无目的继续抓取海量文献 |

建议候选知识必需包含：问题/前置、适用和不适用条件、最小实验、Oracle与反证、预期产物、成本与停止条件、来源/证据、版本/复验期限、至少一个正例与一个易误判反例。可执行脚本与自然语言卡分开评测；新内容若只是旧卡换措辞，应合并或拒绝候选。

### 9.2 一个检索/版本解析面，多种读取适配器

统一顺序为：**Program与发布范围 → 生命周期/当前版本 → 适用前置与环境 → 相关性召回 → 可信实绩及成本 → 上下文预算与去重**。`exp_search/kb_search/vc_get/know_retrieval_explain`仍可保留用户接口，但共用政策与版本解析，不各自实现不同规则。

没有上下文时可返回“待补前置的参考材料”，不能把受限发布当已适用策略。每条实际注入内容带不可变引用和选择原因；未选内容可解释排除原因。全局AGENTS只保留工具/流程的短规则，目标事实和动态卡按任务加载。知识检索延迟、内容token与任务收益一起计入成本，避免“检索越多越聪明”的假设。

### 9.3 真实候选评测与消融

- **合同层**：验证schema、作用域、来源、版本、状态、幂等、失败恢复与撤回。必须通过，但通过不代表能挖洞。
- **行为层**：固定模型、工具、请求集、规则版本与预算；运行候选内容驱动的实际计划。候选空白、错误适用前置、关键步骤删除应产生可观察结果变化，否则评测未真正覆盖知识。
- **端到端层**：受控业务服务包含vulnerable/patched/公开功能/失效身份/代理故障/动态响应/OOB失败；执行方不知道漏洞标签，独立裁判读隐藏真值。输入从合法业务入口开始，不能直接把隐藏答案注入候选判定。
- **对照层**：A为冻结的当前可用知识，B为修复后知识；必要时增加“无该卡”消融定位增益。同一类任务随机/配对分组，记录输入差异，禁止候选看见holdout答案。
- **真实授权试点层**：采用§8的小批请求，固定观察窗；比较有效实验、可信positive、材料质量和成本。真实目标是否有漏洞不是可控制变量，短期零accepted不能证明知识无效，持续零有效实验则必须停止扩展。

报告必须同时给出TP/FP/FN/TN、unknown/blocked/infra/inapplicable、前置成功率、验证精度、可测召回率、独立复现率、成本分布和样本数。阳性样例被系统报unknown仍属于未检出，不能从召回分母中删掉。没有已知真值的真实目标不计算虚假的“召回率”；小样本报告区间，不宣称统计显著。

### 9.4 自主运行与发布纪律

学习调度由高价值缺口和已审校结果触发，日汇总负责去重与回顾，不重复制造卡片。过程为 `gap/episode → candidate revision → 真实评测 → 审批/灰度release → 原任务重试或后续采用 → 收益回流 → 扩大/撤回`。保留已有发布权限与摘要绑定；本方案不改变现有授权边界。

灰度限定一个Program/适用族与时间/预算；失败可只撤回该release，保留证据和评测。扩展条件是可信增益、无新增误报/越界/成本失控，而非卡片数、发布数或总结篇数。文献回流、生命周期复验、失效标记继续运行，但要分别显示它们的维护结果和能力结果。

### 10.1 推荐顺序

**第一段：阻止无效放大。** WP01目标/前置硬约束、WP02弱判定封口、WP03执行归因/预算、WP10最小可见性优先；同时准备WP04账号和业务请求，WP06只做存量审校。C3接近耗尽时不按旧目标自动追加，先核对目标漂移与剩余工作。

**第二段：打通一条可复现业务纵切。** WP04→WP02独立复现→WP06材料出口；WP05按有效实验排序，WP07把该链路真实采用和结果接通。先做一个漏洞族的完整闭环，再推广其他适用族；目标是减少未执行/不成立实验，而非通过放宽confirm获得正例。

**第三段：证明学习收益，再扩规模。** WP08/09完成真实评测与灰度，WP12审查试点；通过§13门槛后扩大业务线/项目。WP11只针对测得瓶颈实施。若升级候选正在冻结，按§13.3独立排期，不混入未封存代码。

### 10.2 每个工作包必须交付的证据

## 11. 存量提交SOP与Campaign 3决策

### 11.1 全量分诊和真实提交SOP

1. **对账与归属**：分页取全部confirmed未提交项、报告及历史任务，核对外部已有工单。使用当前数而非硬编码44/38；重复草稿不重复占待审量。每项确定Program/接收规则版本、证据来源、负责人和审校人。
2. **证据复核**：从受限存储追溯旧run/证据，修迁移映射；证明合法请求、完整步骤、前置和业务影响。可独立复现者前进；证据无法恢复记明确阻塞，不宣布不存在或伪造补齐。
3. **分诊**：ready、需补证据、需规则确认、重复、过期、技术反证、不接收分别记录。优先接收价值高、证据/授权即将过期且材料齐全的项目，同级按等待时间；不是只按严重度标签。
4. **出稿**：报告引用同一finding/证据版本，包含范围、前置、可复现步骤、对照、影响、证据、建议及去重依据。缺失字段阻止ready，不由模型猜写；脱敏副本保留证明力。
5. **独立审校**：审校者复核关键安全属性、反证、SRC接收和报告可读性；审校与自动原始判定可区分。建议首次分诊1个工作日内、补证计划2个工作日内明确；这是运营SLA提案，需按实际人员绑定。
6. **外部提交**：由具备该项目提交权限的运营者在既有授权流程内执行，记录工单/可核验回执、时间、平台、内容摘要和报告版本。本次审查没有发送任何报告，也不替用户新增外部提交授权。
7. **本地回写与失败处理**：平台成功后调用vuln_submit记账；失败先查平台是否已创建，避免重发。平台登录/限流/验证码/接口不支持属于运营阻塞，不判漏洞失败。
8. **反馈与结案**：accepted、duplicate、invalid、out_of_policy、need_more_info、reward分别记录，补材料复用原工单。对账外部状态与本地记录，反馈归因至技术、接收、材料或时效，进入相应知识/规划改进。

验收是**每条有可信去向、责任、下一动作及证据**，外部已提交项都有回执且无重复发送。没有符合条件的存量漏洞时应诚实留下“本轮零可提交”，不能把队列清空当产出。

## 12. 容量、查询和面板：只优化影响发现闭环的瓶颈

### 12.1 先修完整可见性

`dashboard-rpc.kbList`传q而`kb_list` schema不接受，是明确契约问题。第一步使真实RPC查询成功：短期去掉不支持参数并明确搜索能力，或同时把q从schema、SQL、total到UI完整接通；不能只mock掉错误。第二步处理handler先取500再由bus切页，避免第501项永不可见。

候选/提交/任务/审批/报告/知识/资产族列表逐一核对：SQL筛选在LIMIT前、稳定排序加唯一键、count与rows同谓词、参数上限一致。后端已分页时返回`meta.paged:true`避免总线再次切片；维护扫描也要游标跑完全量。用超过200/300/500行且跨Program/状态的数据验证最后一页、筛选后总数、空页和边界项。

### 12.2 面板应该回答“哪里没走通、下一步是什么”

首页分阶段显示：合格资产→健康请求→前置满足→实际执行→可信判定→独立复现→可提交→外部提交→平台认可，同时列unknown/blocked和成本。可下钻到attempt、证据、责任人与恢复条件；知识页显示当前实际采用版本及可信样本，不用卡片总数代替学习能力。

隐藏页面暂停轮询，每视图单个在飞请求，过期响应丢弃，恢复可见时刷新；缓存键含Program/筛选/权限/版本，写后明确失效。错误保留上次成功时间与错误提示，不伪装成零记录。独立测请求数、p95延迟、主服务CPU/事件循环/SQLite等待，优先削减重复全表扫描。

### 12.3 FTS与查询优化的实际起点

现状是exp_fts为external-content索引、kb_fts为独立正文索引，kb_docs没有body列；不能直接给不存在的body建索引。`ftsSearchKb`在MATCH后仍补LIKE，全量embedding扫描也存在。先在脱敏副本上测查询计划和中文/英文/标点/短词语料，再决定优化，不把“有FTS”误当搜索已经足够快或相关。

- 先修生命周期/范围筛选和完整分页，再在热点查询上比较MATCH、有界LIKE fallback、必要的trigram或其他分词方案；CJK短词、标点、空串/非法FTS表达式有明确语义。
- 索引召回后需保留相关性；不足K才做有界补召回，避免无条件全表LIKE覆盖排序。向量候选先限作用域/生命周期并缓存，规模和延迟确实需要时再引入专门索引。
- 对候选、资产、任务、报告等新增FTS逐域测实际收益；索引不是免费写入，比较写延迟、WAL增长、checkpoint和后台任务冲突。
- 回填使用内容来源+digest+游标，事务分批，保存基线水位并补增量；新旧索引影子比较覆盖、正确性与延迟，失败回退查询开关/派生索引。
- 回退不恢复整库覆盖上线后的业务写入；保留原内容、证据和增量。损坏索引可重建，未被索引的条目有可见失败列表。

### 12.4 虚拟化启动条件

默认先服务端每页50–100行。只有分页、请求缓存和表格轻量化后仍能测到DOM渲染瓶颈，才对单个高频列表引入虚拟滚动。验证变高行、展开详情、勾选、键盘焦点、返回定位和长中文文本；保留普通分页回退。虚拟化解决渲染，不能解决查询报错、后端500行截断、知识不适用或漏洞证据不足。

### 14.3 运行数据的复核口径

本次远程操作只用PATH中的`spool exec csai`；SQLite URI使用`file:/opt/silkspool/dsh/data/asset-graph.db?mode=ro`，并设置`PRAGMA query_only=ON`、3秒超时。查询只输出聚合/有限字段，未导出目标凭据或完整敏感响应。建议后续审计对同一批cohort建立受控只读快照；本次连续查询不冒充原子快照。

典型口径如下（只读SQL；时间是毫秒，实施复核时替换采样时刻/窗口）：

```sql
SELECT method, COUNT(*) AS n FROM endpoints GROUP BY method;
SELECT auth_state, COUNT(*) AS n FROM endpoints GROUP BY auth_state;
SELECT COUNT(*) AS populated_params FROM endpoints
WHERE params IS NOT NULL AND trim(params) NOT IN ('', '{}', '[]', 'null');
SELECT status, noise, COUNT(*) AS n FROM findings GROUP BY status, noise;
SELECT COUNT(*) AS total, COUNT(task_id) AS linked FROM findings;
SELECT date(started_at / 1000, 'unixepoch') AS day,
       COUNT(*) AS run_rows, SUM(ok = 1) AS ok_rows,
       SUM(spent_tokens) AS recorded_tokens
FROM task_runs GROUP BY day ORDER BY day;
SELECT outcome, COUNT(*) AS n FROM learning_episodes GROUP BY outcome;
```

资产新鲜度用固定采样时刻减7天比较`last_seen`，不要直接把毫秒传给SQLite的unixepoch秒转换。Cost按task.campaign关联再按任务类型/目标分类汇总，未记录token保持NULL；回收行按统一note及补丁时间窗过滤，再核worker关联。知识采用ID应按artifact_kind连接对应仓，不能只因是字符串就认作有效ID。草稿数按report注册表及唯一文件路径交叉核查；证据存在性按标准引用保守解析，旧格式另审。
