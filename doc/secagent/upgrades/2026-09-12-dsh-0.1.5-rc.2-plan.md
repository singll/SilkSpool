# DSH 0.1.5-rc.2 升级与 SilkSecAgent v5 优化方案

> 日期：2026-09-12；状态：**方案待实施，生产仍为 0.1.2-rc.1**
> 范围：csai 的 SilkSecAgent；目标 DSH **0.1.5-rc.2**；架构继续采用 **v5 的 14 业务域 + 总线**。
> 配套：[预检与执行记录](2026-09-12-dsh-0.1.5-rc.2-record.md) · [自学习与漏洞探测设计](2026-09-12-self-learning-design.md) · [升级时间线](README.md)
> 上位规范：[00-conventions](../v5/00-conventions.md)；本方案没有修改已定稿的域契约，也不表示新功能已经上线。

## 1. 建议与实施顺序

**建议直接以 rc.2 为升级目标，先解决兼容与回滚，再推进可验证的自学习闭环。** rc.1 的变更已包含在 rc.2 内，无需在生产先装 rc.1 再装 rc.2；会话格式迁移由上游迁移目录处理，能否跨越当前历史格式必须在副本上验证。

执行顺序：

1. **U1：适配与升级工具加固**，尤其是 Session 列表、persona、版本锁与完整恢复点。
2. **U2：隔离预演**，验证 V3 历史读取、插件、双 profile、实际 Web/worker 功能和回滚。
3. **U3/U4：生产切换和观察**，通过验收后才更新运行态版本与完成状态。
4. **L0–L6：学习与探测增量**，按专项设计先修评测/证据基础，再加入知识候选、独立评测、受控晋升和看板。

L0 的现存缺陷可在旧 DSH 上先修；它不必等待 rc.2。平台升级和学习效果分别验收，避免同时更换模型、提示词、评测集与调度策略后无法归因。

**本次检查结论**：线上基础验收 25/25，通过不代表学习闭环完整；关键代码抽样与部署态 15/15 一致。现状详见配套 record。

| rc.2：反馈弹窗确认、失败保留填写内容 | 可用作人工反馈入口；不是自动学习实现 | 建本地反馈到 know/eval 的归因桥，处理修改/撤销 |
| rc.2：交付文件卡片和图标/间距优化 | 改善证据/报告查看 | UI 冒烟，非检出能力提升 |

**版本锁注意**：检查时 GitHub 最新为 rc.2，npm `latest` 仍为 rc.1。必须显式选择 `0.1.5-rc.2`，记录实际解析的依赖和完整性摘要。不要用 `latest` 或无版本参数的快捷升级来表达此次目标。

## 4. 必须完成的适配

### 4.1 Session 与 persona

**Session 适配入口**放在 sec-suite 的宿主适配层，由以下三个消费者共用：

- sessionsList：`snapshot.header.id / createdAt`；
- reconcileWorkspaceSessions：`snapshot.header.cwd / id`；
- findWorkerSessionId：`snapshot.header.cwd / createdAt / id`，并保留来源/运行窗口校验。

明确区分 0.1.2 的平铺返回与 0.1.5 的 snapshot，遇未知形状报诊断，不静默生成空跳链。详细轨迹通过 `open(id, 'read')` 获取并在 finally 关闭；不自行解压重写 V3，不抢占现有 Session 的写锁。worker 完成后优先使用可核实的 session_id，时间窗反查只作有告警的后备。

**Persona 适配**：

1. 从目标安装树解析 `@deepseek-ai/dsh-agent-presets` 的 shipped standard；旧 `@deepseek-ai/dsh/config/agent-presets/standard` 不再是可靠来源。
2. 以 YAML 结构修改 `prefix/suffix`，替代 text 正则；完整保留角色职责、当前工作区、授权与工具指导。
3. scheduler 从同一份结构读取，不再静默退化为无角色。升级 persona_version，原子生成 7 个预设。
4. 稳定身份与基本纪律放 prefix；工作区和按需知识放后续受控内容。保持 `complete:false` 和运行上下文开启，防止压掉授权/沙箱/工具指导。
5. discipline-audit 扫描范围增加“最终拼装 prompt”和 scheduler 源模板；修复仍存在的 finding_add 引用，再重新观察别名使用。

对应文件：[sec-suite](../../../bundles/dsh/templates/dsh-plugin-sec-suite.js)、[scheduler](../../../bundles/dsh/templates/dsh-plugin-sec-suite.scheduler.js)、[seed-presets](../../../bundles/dsh/templates/seed-presets.sh)、[discipline-audit](../../../bundles/dsh/templates/data-seed/scripts/discipline-audit.py)。

### 4.2 插件与补丁

- 固定并验证 app、web、headless、用户 preset 的实际依赖树；排查旧 peer 依赖导致的多份 Cordis/DSH 核心包，不能只看最外层 dsh 版本。
- auth-gate、model-failover、dsh-bill、browser fork 单独记录兼容结果。fork 保留 CDP、登录态和 SEC_FLOW_PROXY 契约。
- settings-mirror、pnpm patchedDependencies、reasoning_content 补丁做“仍需要 / 已被上游修复 / 需要适配”清单。补丁失配不能只 warn 后宣告完整成功。
- 自研直接 `ctx.agent` 引用为 0；`exec.agent` 仍是 ToolRunContext。不要为 release 的接口删除误改保留接口。
- Web 初期保留现有入口，确认 primitives、RPC 身份和 sessions.open；全局 main/panellist 和逐域视图改造放 L6，避免把 UI 重写变成此次平台升级的必经依赖。
- 不启用额外 Codex/Claude worker 后端；继续用既有 DSH + pi-ai/Bellkeeper 路由。模型变更应作为有独立评测的后续增量。

### 4.3 出站与反馈

**目标交互继续经过 scope → exec 的授权与预算检查。** 公共情报检索和项目探测分开定义允许的目标、凭据与出口；HTTP_PROXY 只解决路由，不能替代授权。

rc.2 的实际代理实现还有以下约束：

- 不支持的代理值会告警并可能改为直连，不能当成 fail-closed。部署验证必须把不合法协议/URL作为失败处理。
- NO_PROXY 用明确的回环、Bellkeeper 和必需基础设施主机/IP；不照抄 `192.168.7.0/24`。回环在上游被绕过，仍应测试 CDP、本地 webhook 与代理网关。
- plain fetch/pi-ai 与自建 HTTP 客户端、子进程路径不完全相同；上游特别注明 OTel HTTP 出口并不跟随同一 dispatcher。原生 web_fetch 也不能借由“已经过代理”免除 Scope 检查。
- 对实际使用的 fetch、模型请求、浏览器、CLI 工具分别记录出口验证；所有会接触项目的入口需强制 Scope，而非只靠 prompt 提醒。

**反馈应进入本地学习闭环**。rc.2 的 message-feedback 记录在 canonical Session 日志，默认不会进入模型历史，也不会自己更新经验卡。接线按专项设计，不把“点赞按钮可用”当作自学习完成。

上游 OTel 的 FEEDBACK_ONLY 会在新反馈/编辑/撤销时释放包含上下文的 canonical prefix。面向 SRC 的部署应显式设置 `@deepseek-ai/dsh-session-telemetry-otel` 的 `config.mode: DISABLED`（实际 row id 以解析后的组合树为准），并分别核对可选 session-log-deepseek、插件清单上报。旧版一个 `enabled:false` 不能覆盖新增通道。保留本地反馈采集及已授权的模型调用。

## 5. 升级执行设计

### 5.1 先修升级器

当前 [dsh-upgrade.sh](../../../bundles/dsh/templates/dsh-upgrade.sh) 不足以承担 V3 切换，U1 必须补齐：

| 缺口 | 必须实现的行为 |
|---|---|
| 在线 tar 且失败只 warn | 停止新派单、排空 worker、冻结相关状态写入后建立恢复点；备份失败退出，不切版本 |
| 配置快照漏 pnpm-lock/workspace/patch | app + profiles 的 package/锁/workspace/patch、插件锁与配置一并归档；保存原文件权限与软链关系 |
| 只有版本回滚 | 恢复旧运行产物、配置、会话代际和必要领域状态的同一恢复点；启动后再验收 |
| CI 下 rollback 重新 install | 优先切回完整旧产物；必须安装时用经过验证的旧锁/patch离线或冻结恢复，不靠 latest |
| 活动 app 内安装 | 预先准备、验证候选产物；切换窗口只执行已验证步骤，不临时解决依赖 |
| 冒烟只查 HTTP/两个插件名 | 增加双 profile 的运行注册、实际查询/安全拒绝、worker、Web、版本一致性检查 |
| projcache 版本硬改 | 对 V3 使用上游迁移目录；未知格式拒绝并保留原件 |
| 日志输出访问 token | 升级记录只留验证结果和受控取用方式，不把访问 token 写入可传播记录 |

**部署路径注意**：[ScriptDriver.Upgrade](../../../internal/engine/script_driver.go) 会先 pull 配置、再推模板、最后跑升级脚本，而且 CLI 仅传 force，不传版本。原样使用可能在恢复点之前覆盖旧脚本，又选中 npm latest=rc.1。

因此 U1 的执行手册必须通过 **spool** 完成“先保存旧产物，再暂存候选脚本/依赖，再显式版本切换”。可使用 `spool exec` 分阶段操作，不要求改写 spool 的 Go 核心。**不能把全量 setup 当成无副作用的预检命令。**

### 5.2 隔离预演

创建生产恢复点的隔离副本，并使 app、DSH_HOME、SEC_BASE_DIR、SEC_DATA_DIR、profiles、模型凭据、代理、端口和所有写路径都指向预演环境。

仅改变 DSH_HOME 不够：现有插件默认路径和 profiles 的 file:/软链可能仍指生产。启动前验证路径解析结果，关闭真实调度、timer、webhook、vault 回写及项目网络出口；使用 fixture/test Scope 和测试身份。副本上的正式迁移不得接触生产 Session 锁。

预演内容：

1. 对**全部快照日志**做官方迁移的可读取性检查；按长会话、分支、含附件、工具错误、中断、多轮恢复分层抽样复核语义。
2. 覆盖 V0/V1 经 V2 到 V3 的适用链，不靠文件后缀猜格式；被拒扩展记录具体 session/错误码，在副本定位，不在生产强修 header。
3. 校验迁移前后逻辑 Session ID、标题、工作区归属、父子关系、证据链接及未完成轮次处理。V3 插入系统消息后事件数可变，不能要求总行数相等。
4. 对同 Session 双写的拒绝、读观察并存、停止/崩溃后释放写锁进行测试。
5. 按 §6 跑兼容检查，**恢复旧产物+旧会话快照并读回成功**后才允许 U3。

### 5.3 生产切换顺序

1. 根据当前 task_scheduled/worker 状态选窗口。活跃任务已不是旧文固定的四条 03:00/04:00 链，不能只按历史时间猜空闲。
2. 暂停新派单，等待在飞 worker 结束；记录被暂停的 timer/接收器。排空或可靠暂存会写数据库/文件的 webhook、采集及治理事件。
3. 停止相关写进程；确认没有同库/同会话的写者。对 SQLite 做一致性备份并检查完整性；同时保存 Session、storages、工作区映射、Scope、凭据引用、审计/outbox、知识资产与配置。
4. 保存 data/sessions 与根 sessions 的归属清单。对 findings/卡片/报告仍引用的 results/flows/截图/OOB 证据保留完整内容或可恢复对象清单；旧脚本笼统排除 results/flows 不足以保护长期学习证据。
5. 切到预演通过的 rc.2 产物及适配插件，执行正式迁移与启动验收。期间保持调度和外部写入暂停。
6. 在同一发布中对齐 setup.sh 的 DSH_VERSION、version-watch 的已知版本、app/profiles 锁、patch 和预设版本。**旧 pin 的 setup 不能在新会话上运行，否则可能降回旧版。**
7. 冒烟全通过后恢复必要写入与调度，登记实际启用时间、版本、快照、代码提交和观察截止时间。

显式版本调用的现有语法如下，**只在 U1 的升级器加固并通过 U2 后使用，本次未执行**：

```bash
spool exec csai 'bash /opt/silkspool/dsh/dsh-upgrade.sh --version 0.1.5-rc.2'
```

模板发布仍遵守仓库 → `/opt/SilkSpool/bundles/dsh/` 运行时副本 → spool 的通道；每个调用点是否会安装/重启必须在 U1 执行手册写清。不得提前运行旧全量 setup。

### 5.4 回滚条件和恢复范围

| 触发 | 动作 |
|---|---|
| 备份/恢复预演失败、未知会话格式、关键插件不能加载 | 不进入生产切换 |
| Scope/actor/证据守卫回归，Session 历史损坏，核心 Web/worker 不可用 | 保持写入冻结，回滚整套发布并重新验收 |
| 模型请求、会话锁、调度收尾持续失败，超过预先记录的可用性预算 | 停止派单并按已演练流程恢复；不能靠无限自动重试拖过窗口 |
| 学习候选效果下降，但平台兼容正常 | 只撤销对应知识/选择策略版本，不回滚 DSH 或丢弃新会话 |

V3 切换后的回滚不能只修改 package.json。新版即便保留旧代原件，也不能保证旧运行时会正确选择它们。

**切流前冒烟阶段**尚未重新放行业务写入，可恢复统一冻结点。**切流后**已有新增任务、Session 或裁决时，先冻结并额外保存新状态；V3 新会话作为隔离存档保留，旧版不可直接续写。领域库若 schema 兼容且一致性已验证可保留，否则恢复冻结点后按业务事件逐项对账重放；外部提交/请求不得盲目重放。记录受影响时段和实际 RPO，不能声称自动零损失。

## 6. 升级验收矩阵

| 组 | 验收 | 放行条件 |
|---|---|---|

先在隔离环境完成 U-A～I；生产只运行经过评审的最小功能冒烟。升级后的漏洞检出评测由 L3 单独执行，7/7 网关用例不能替代它。

**观察期**：建议至少 72 小时，覆盖每条活跃 interval 的两个实际周期；#24 是周任务，若未到期，则执行受控等价复盘验收并继续保留周周期观察。记录任务收尾、事件积压/partial、错误类型、会话加载 P95、token/有效产出成本。性能先测旧版对照，再设阈值，不能用现有计数推定收益。
