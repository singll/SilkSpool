## 零、结论速览（先回答三组问题）

| # | 问题 | 结论 |
|---|---|---|
| 1 | **0.1.7 要不要升？** | **要，但不是无缝升级**。上游 22 项「其他变更」中含 6 项直接影响本平台的破坏性变更（Session V4、Agent Preset 机制替换、settings 持久化迁移、官方 DeepSeek 适配器 Messages-only、配置热更取消回滚、插件兼容检查）；另有 4 项 P0 阻断在**我们自己的工具链硬编码**（版本门禁、Session V3 断言、preset 目录、settings 镜像补丁）。预估 U0–U4 完整周期同 0.1.5 升级量级。 |
| 1b | **dsh 支持官方定时任务吗？** | **支持**。`@deepseek-ai/dsh-schedule` 自 0.1.5-rc.2 起存在（session 级提醒），0.1.7-rc.1/rc.2 大幅增强为 **host-wide durable reminders**：6 种选择器（after/at/every≥60s/daily/weekly/cron）、交付历史（30 天/200 条）、管理页；**默认关闭**（Web `schedule`/`time-context`/`ui-schedule` 三个 row `disabled: true`）。 |
| 1c | **自研定时任务能迁到官方吗？** | **不能/不应迁移**。官方 schedule 的语义是「到点向会话 inbox 追加一条提醒消息（followup）」，**不是受治理的任务执行**；官方 README 明示它**不能只在 headless/SDK 组合挂载**（需要 Host Web Session controller + session persistence），而我们所有定时任务是调度器→headless worker 无人执行。迁移会丢失 scope/预算/审批/证据/任务闭环。**专项（Campaign）更不可迁移**（节奏权唯一归 campaign tick、子任务禁 interval）。结论：**双轨分工**——自研 task 域定时保持为「受治理无人执行面」，官方 schedule 可选做「交互式会话提醒面」（P2）。 |
| 2 | **大数据量问题严重吗？** | 严重但可治。实测 `event_outbox` 13.1 万行（delivered 13 万且无清理路径）、`bus_subscription` 6.1 万行、`idempotency` 5.9 万行（**超设计上限 1 万行 5.9 倍，`bus_prune` 从未被调度**）、`assets` 10 万行、`sessions` 515M、`results` 594M、`backups` 2.1G；另有 `ledger` 覆盖指标被 500 行截断导致**指标失真**（bytedance crawl 分母 500/69605、meituan `need_login` 全量 4 个在采样里为 0）、`vuln_list`/`report_list` SQL 不落 LIMIT、审计只能看末尾 256KB、前端固定 200 窗口静默漏数据。方案见 [§二](#二全域大数据量优化方案)，分 S0 数据治理 / S1 查询索引 / S2 UI 容量三阶段。 |
| 3 | **文档漂移存在吗？** | 存在，且集中在任务域。36/37/40/41 号补丁改变了 canonical 口径（并发上限 4→12、task_reap 不发事件、`dir` 已生效、task_scheduled 仅 interval、spent_tokens 已归因），但 `05-task.md` §1.2/§1.4/§1.5/§2.1/§2.4/§2.6 仍写旧值；34 号（预算闸在线配置）未回填 05、31 号（升档通道放宽）未回填 09、kind 注册表 8→11 未更新、CONTEXT「5 kind/四区块」过时。完整 35 项清单见 [§三](#三文档一致性核查与回填清单)。 |

**建议批次**：B0 文档回填（低风险，先行）→ B1 大数据 S0 治理（无 schema 破坏，旧版可做）→ B2 大数据 S1 索引（旧版可做，带备份）→ B3 0.1.7 U0–U4（工具链改造 + P0 插件）→ B4 大数据 S2 UI + 官方 schedule 可选启用。

|---|---|---|

### 1.3.3 迁移判定与建议

**结论：不迁移自研定时任务；官方 schedule 作为可选的「会话提醒面」补充（P2）。**

理由（按重要性）：

1. **执行模型不同**：官方是「提醒消息」，自研是「受治理的无人执行」。把 #16/#17/#24 迁到官方后，将不再有 worker 执行、不再写 `task_runs`/证据/成本、不再过 scope/预算/审批——等于放弃平台的核心闭环。
2. **运行环境不兼容**：官方 schedule 不能在 headless-only 组合挂载，而我们的定时执行全部发生在 headless worker（`bin.js --profile headless …`），Web 会话只是看板与人工入口。
3. **专项明确不可迁移**：Campaign 子任务本就禁 interval（INV-C7，`E_CAMPAIGN_INTERVAL_FORBIDDEN`），节奏权唯一归 `campaign_tick`；且派生/放行依赖预算闸与审批（`campaign-autonomy`/`campaign-budget-extend`），官方提醒无这些概念。
4. **当前存量定时任务均为执行/治理型**：csai 实查 interval 任务为 #16/#17（每日 recon，喂专项 ledger 缺口）、#24（周知识复盘），以及已 blocked 的 #19/#37/#100007/#100008（待专项接管，保留可恢复）——全部需要无人执行与证据链。

**可选采纳（P2，与自研并行）**：升级完成后启用 Web profile 的 `schedule` + `ui-schedule` row，用于**运维提醒**类场景（例如：审批积压、供给熔断、专项异常、额度预警）。这些提醒的接收者是 Web 会话（用户/在值 agent），与自研任务执行面分工明确：
- 官方 schedule = 提醒到会话（人在回路）；
- 自研 task interval = 受治理的无人执行（机器闭环）。
另注意：启用后「有活跃提醒的会话归档会被拒绝」，这是官方行为，需在 UI 使用说明中标注。

**不采纳的替代方案**：不建议把「官方提醒 → 会话 agent 自动 task_create」当作无人值守路径（依赖会话可恢复、Web 进程在线，且绕开直接执行通道的可靠性更低）。
