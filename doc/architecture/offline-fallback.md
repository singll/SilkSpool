# 离线托底与应急访问

> Headscale VPN 不可用时的应急访问专题。
> **当前状态**：本地网络直连可作为已验证的托底路径；本文档仅说明应急访问策略，不代表要在日常运维中绕过 `spool.sh` 规范。

---

## 适用场景

当 txhk / Headscale 出现故障，导致无法通过 VPN 访问内网主机时，使用本专题中的托底方式维持最基本的管理与排障能力。

日常运维边界与基础设施总览以 [infrastructure.md](infrastructure.md) 为准。

---

## 当前可用的托底路径

### 1. 本地网络直连（首选）

**适用场景**：管理员处于同一局域网内。

**当前结论**：该路径已验证可用，是当前正式的离线托底方案。

可直接访问以下主机：

```text
knowledge   192.168.7.220
keeper      192.168.7.230
aigateway   192.168.7.110
```

如需访问 Web 服务，优先继续通过既有域名与反向代理入口访问；当仅 VPN 控制面异常而局域网仍正常时，内网侧服务本身不受影响。

### 2. 公网端口映射（仅紧急临时手段）

**适用场景**：无法进入局域网，且 VPN 故障持续时间较长。

**原则**：只作为临时应急手段，不作为常态方案。

**限制**：
- 仅在确有必要时开启。
- 使用后立即关闭映射。
- 不暴露数据库等敏感服务。
- 优先使用 SSH 密钥与最小暴露面。

### 3. 备用 VPN（保留为未来选项）

当 Headscale 长期不可用且现有托底路径不足时，再评估备用方案，例如：
- WireGuard 直连
- Tailscale
- Cloudflare Tunnel

当前没有实施需求。

---

## 应急操作建议

### 最小恢复顺序

```text
1. 先确认是否仍可在局域网内访问目标主机
2. 通过本地网络执行必要的 spool.sh / 状态检查 / 日志查看
3. 排查 txhk 与 Headscale 本身故障
4. 仅在无法进入局域网时，才考虑临时公网映射或备用 VPN
```

### 操作边界

- 优先恢复 VPN 控制面，而不是长期依赖替代通道。
- 即使处于离线托底场景，也应尽量遵守项目运维红线。
- 如涉及高风险操作或有状态服务变更，仍需按常规审批。
